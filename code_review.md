# Code Review — Camera Video Map API



## 1. Архитектура и структура проекта

В целом структура приятная. Видно, что ты думал о разделении ответственности: есть роутеры, сервисы, репозитории, доменные модели — всё по своим папкам. Это уже хорошо, большинство начинающих пихают всё в один файл.

**Что хорошо:**
- Слои явно разделены: `api/v1/routers` → `domain/services` → `data/repositories` → `data/models`
- `BaseRepository` с generics — правильное решение, не дублируешь CRUD в каждом репозитории
- Зависимости собраны в одном `dependencies.py` — удобно



**Нет слоя абстракции для MinIO.** MinIO-клиент используется напрямую в `VideoService` через `get_minio_client()`. Это нарушает принцип инверсии зависимостей: сервис знает о конкретной реализации хранилища. В идеале сделай что-то вроде `StorageRepository` или `FileStoragePort` с методами `put_file`, `delete_file` и т.д. Тогда в тестах не придётся делать `monkeypatch` на модуль — просто подменяешь зависимость.

```python
# Сейчас:
client = get_minio_client()
await asyncio.to_thread(client.fput_object, ...)

# Лучше:
class MinioStorageRepository:
    async def put_file(self, bucket: str, key: str, path: Path, content_type: str) -> None:
        await asyncio.to_thread(self._client.fput_object, ...)
```

**`CameraService` принимает `redis_client` без типа.** В `__init__` параметр объявлен просто как `redis_client` без аннотации. Для mypy и читаемости лучше указать `Redis | FakeRedis` или завести протокол.

**`ensure_bucket` вызывается без `await` в lifespan.** Это синхронная функция — ок, но в `main.py` она вызывается без обёртки `asyncio.to_thread`, хотя под капотом делает сетевой запрос к MinIO. Это блокирующий вызов в async-контексте. Оберни в `asyncio.to_thread`:

```python
await asyncio.to_thread(ensure_bucket, settings.MINIO_BUCKET_VIDEOS)
```

## 2. FastAPI: зависимости, схемы, middleware

**Что хорошо:**
- Dependency injection выстроен грамотно: репозитории и сервисы создаются через `Depends`, не вручную
- Аннотированные типы (`Annotated[X, Depends(...)]`) — современный и правильный подход
- Pydantic v2 используется корректно, `from_attributes=True` там, где нужно

**Что стоит улучшить:**

**`get_redis_client` возвращает не `AsyncGenerator`.** В `redis_client.py` есть функция `get_redis` с `yield`, но в `dependencies.py` используется `get_redis_client` — обычная функция без `yield`. Это нормально работает, но тогда функция `get_redis` в `redis_client.py` нигде не используется и просто висит мёртвым кодом. Убери её или используй.

**Маппинг в роутерах дублируется.** В `camera.py` (роутер) и `videos.py` ты вручную конвертируешь ORM-объект в Pydantic-схему через конструктор с перечислением каждого поля:

```python
# camera.py роутер — вот это:
return CameraListItem(
    id=camera.id,
    camera_id=camera.camera_id,
    camera_name=camera.camera_name,
    ...
)
```

Раз у тебя `ConfigDict(from_attributes=True)` — используй `CameraListItem.model_validate(camera)`. Правда, `video_count` в модель так не пробросишь напрямую, но можно через `model_validate({'video_count': count, **camera.__dict__})` или добавить вспомогательный метод. Текущий подход — это ручной труд, который легко сломать, если добавишь новое поле в модель и забудешь добавить его в маппинг.

**CORS настроен слишком широко для прода.** `allow_origins=settings.CORS_ORIGINS` — это хорошо, но по умолчанию там `["http://localhost:3000"]`. Убедись, что в проде это переопределяется через переменную окружения и не остаётся на дефолтном значении. Также `allow_methods=["*"]` и `allow_headers=["*"]` — для прода стоит сузить.

**Нет rate limiting.** Это не блокер для учебного проекта, но `/api/v1/auth/login` и `/api/v1/auth/register` прямо просятся под ограничение. Можно добавить `slowapi` буквально за 20 строк.

**Нет middleware для логирования запросов.** Сейчас логируются только ошибки. Было бы хорошо иметь middleware, который пишет хотя бы `method`, `path`, `status_code` и время обработки каждого запроса.

## 3. Асинхронность

**Что хорошо:**
- SQLAlchemy используется с async-движком (`asyncpg`), сессии правильно создаются через `async_sessionmaker`
- MinIO (синхронный клиент) оборачивается в `asyncio.to_thread` — правильно
- ffprobe/ffmpeg запускаются через `asyncio.create_subprocess_exec` — тоже верно

**Что стоит улучшить:**

**`verify_password` / `get_password_hash` — blocking I/O в async-контексте.** bcrypt — CPU-bound операция, которая блокирует event loop на десятки миллисекунд. При нагрузке это будет деградировать. Оберни в `run_in_executor`:

```python
import asyncio

async def verify_password_async(plain: str, hashed: str) -> bool:
    loop = asyncio.get_event_loop()
    return await loop.run_in_executor(None, pwd_context.verify, plain, hashed)
```

Или используй `argon2-cffi` — у него есть async-вариант.

**`ensure_bucket` в lifespan — блокирующий вызов**, как упоминалось выше. В lifespan у тебя иначе всё async, а этот вызов торчит как синхронный.

**Пул соединений создаётся правильно** — движок один, `async_session_maker` один, молодец. Это типичная ошибка новичков, ты её избежал.

## 4. Безопасность

**Что хорошо:**
- JWT разделён на access (30 мин) и refresh (7 дней) — правильно
- Куки `httponly=True` — отлично, XSS не достанет токены
- `secure=settings.is_production` — токены не утекут через HTTP в проде
- Пароль хранится хешем через bcrypt
- Секреты читаются из `.env`, хардкода нет

**Что стоит улучшить:**

**Нет авторизации по ролям, и это нигде не обозначено явно.** `GET /api/v1/users` — список всех пользователей системы — доступен любому залогиненному. Это заложено в ТЗ, но стоит хотя бы добавить комментарий, что это осознанное решение, а не забытая проверка. Иначе при ревью у любого проверяющего сразу возникнет вопрос.

**Нет защиты от CSRF.** Куки `samesite="lax"` защищают от большинства CSRF-атак, но это не полная защита. Для production-ready решения нужен CSRF-токен или переход на `samesite="strict"`. Для учебного проекта `lax` — приемлемо, но знай об этом.

**`decode_token` не проверяет `nbf` и `iat`.** Сейчас в токен кладётся только `exp` и `type`. Если токен украдут и немедленно используют — ничего не остановит. Опциональная защита — добавить `iat` и проверять его разумность.

**Секреты в `conftest.py`** — `SECRET_KEY` и ключи MinIO захардкожены в тестах. Для тестов это ок, но убедись, что `.env` с реальными секретами в `.gitignore` и случайно не утечёт в репо.

**`ALGORITHM` вынесен в конфиг как строка без валидации.** Ничто не мешает поставить туда `"none"` или что-то экзотическое. Лучше ограничить:

```python
from typing import Literal
ALGORITHM: Literal["HS256", "HS384", "HS512"] = "HS256"
```

## 5. База данных

**Что хорошо:**
- Alembic подключён (через `entrypoint.sh`)
- Индексы расставлены на полях, по которым фильтруешь (`camera_id`, `video_id`, `uploaded_at`, `email`)
- `expire_on_commit=False` — правильно для async, иначе обращение к атрибутам после commit падает
- Транзакция управляется в `get_db()` — сервисы и репозитории не вызывают `commit()` самостоятельно (кроме теста)

**Что стоит улучшить:**

**Дублирование подзапроса `video_count_subq` в `CameraRepository`.** Один и тот же подзапрос написан трижды — в `list_filtered`, `list_all_with_video_count` и `get_by_id_with_video_count`. Если понадобится изменить логику подсчёта — придётся менять в трёх местах. Вынеси в приватный метод:

```python
def _video_count_subq(self):
    return (
        select(Video.camera_id, func.count(Video.id).label("video_count"))
        .group_by(Video.camera_id)
        .subquery()
    )
```

**`Camera.has_video` — Python-property, не колонка БД.** Сейчас `has_video` вычисляется через `len(self.videos) > 0`, что требует загрузки всех видео в память. В `_build_geojson` ты это обходишь (используешь `video_count > 0`), но сама модель с таким property может ввести в заблуждение: кто-то захочет использовать `camera.has_video` напрямую и получит либо N+1, либо ошибку lazy loading.

**N+1 потенциально есть в `list_camera_analyses` роутере.** Ты обращаешься к `a.video.name` для каждого анализа в роутере. В `AnalysisRepository.list_by_camera` видео подгружается через `joinedload` — это правильно. Но в `get_by_video` его нет. Если кто-то вызовет `get_by_video` и потом обратится к `a.video` — получит lazy load или ошибку. Добавь `joinedload` туда тоже.

**Нет пагинации на уровне ответа API.** Пагинация есть в запросах (`limit/offset`), но в ответе нет метаданных — `total`, `page`, `pages`. Клиент не знает, сколько всего записей. Это не критично, но неудобно при построении UI.

## 6. Производительность и масштабируемость

**Что хорошо:**
- GeoJSON кешируется в Redis с TTL и инвалидируется при загрузке нового видео — правильное решение
- Пул соединений к БД настраивается через конфиг (`DATABASE_POOL_SIZE`, `DATABASE_MAX_OVERFLOW`)
- Файлы загружаются чанками, есть проверка максимального размера

**Что стоит улучшить:**

**Загрузка видео — полностью синхронная по отношению к запросу.** Сейчас upload видео делает всё в одном запросе: сохраняет на диск → запускает ffprobe → извлекает кадр → заливает в MinIO → пишет в БД. При большом файле (2 GB лимит!) это держит соединение открытым очень долго. Правильное решение — `BackgroundTasks` или очередь задач (Celery/ARQ): принять файл, вернуть 202 Accepted с ID задачи, а метаданные извлекать асинхронно.

**`VideoService.upload` создаёт `tempfile.TemporaryDirectory` синхронно внутри async-функции.** Это ок для системного вызова (он быстрый), но стоит знать об этом.

**`has_video` в GeoJSON инвалидируется только при загрузке видео, но не при удалении** (эндпоинта DELETE нет, но на будущее — учти).

**MapLibre тайлы OSM используются без ограничений.** `https://a.tile.openstreetmap.org` — публичный сервер с ограничением по политике использования. Для продакшна нужен либо свой тайловый сервер, либо платный провайдер (Maptiler, Mapbox).

## 7. Обработка ошибок и логирование

**Что хорошо:**
- Есть иерархия исключений (`AppException` → `NotFoundException`, `AlreadyExistsException`, `UnauthorizedException`)
- Глобальный обработчик для необработанных исключений есть
- В обработчике логируется `method`, `url.path` с `exc_info=exc`

**Что стоит улучшить:**

**Логирование не структурированное.** Сейчас используется обычный `basicConfig` с текстовым форматом. Для production это проблема: логи невозможно искать по полям (`user_id`, `request_id`, `camera_id`). Переходи на structlog или хотя бы на JSON-форматтер:

```python
import json
import logging

class JsonFormatter(logging.Formatter):
    def format(self, record):
        return json.dumps({
            "ts": self.formatTime(record),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
        })
```

**Нет `request_id`.** Добавь middleware, который генерирует уникальный `request_id` для каждого запроса и прокидывает его в контекст (через `contextvars`). Тогда в логах можно будет отследить весь путь конкретного запроса.

**`LOG_LEVEL` из конфига не используется.** В `setup_logging()` уровень захардкожен как `logging.INFO`. Ты читаешь `settings.LOG_LEVEL`, но не применяешь. Исправь:

```python
logging.basicConfig(level=getattr(logging, settings.LOG_LEVEL.upper(), logging.INFO), ...)
```

**Нет мониторинга.** Нет `/metrics` для Prometheus, нет трейсинга (OpenTelemetry). Для учебного проекта некритично, но стоит знать о таких инструментах.

## 8. Тесты

**Что хорошо:**
- Тесты есть — и это уже большой плюс
- `conftest.py` грамотно настроен: SAVEPOINT-паттерн для изоляции тестов без полного пересоздания БД на каждый тест
- `FakeRedis` — правильное решение, не нужен реальный Redis в тестах
- Тесты покрывают happy path и edge cases (404, 409, 401, 422)
- Тест на инвалидацию кеша GeoJSON — отлично, это нетривиальная логика

**Что стоит улучшить:**

**Тест `test_upload_marks_camera_as_has_video_on_map` может давать ложный результат.** Этот тест проверяет инвалидацию кеша после загрузки видео. Но если в тесте Redis закеширует GeoJSON при первом запросе, а инвалидация сработает, то второй запрос пойдёт в БД — и тогда тест зависит от порядка. Это сейчас работает, потому что `FakeRedis` простой, но стоит сделать тест явным: проверить, что ключ кеша был удалён после загрузки.

**`_FakeMinioClient` дублируется в трёх тестовых файлах** (`test_api_analyses.py`, `test_api_users.py`, `test_api_videos.py`). Перенеси его в `conftest.py` — один раз как `autouse`-фикстура или как именованная фикстура.

**Нет тестов для негативных сценариев аутентификации через куки.** Например, что будет, если токен истёк? Что если токен подделан? Что если передать access-токен как refresh и наоборот? В `test_security.py` это тестируется на уровне утилит, но на уровне API — нет.

**`sample_mp4` — session-scope фикстура, а `db_session` — function-scope.** Это нормально, конфликта нет. Но если тест изменит файл на диске — другие тесты сломаются. Сейчас такого нет, но стоит иметь в виду.

## 9. DevOps и конфигурация

**Что хорошо:**
- `docker-compose.yml` покрывает все зависимости: PostgreSQL, Redis, MinIO
- Healthcheck для всех сервисов + `depends_on: condition: service_healthy` — правильно, без этого приложение стартует раньше БД
- `entrypoint.sh` запускает `alembic upgrade head` перед стартом
- Переменные окружения вынесены в `.env`, хардкода нет

**Что стоит улучшить:**

**`--reload` в продакшн-команде.** В `docker-compose.yml` команда для `backend`: `uvicorn main:app --reload`. Это флаг для разработки — он перезапускает сервер при изменении файлов и добавляет накладные расходы. Для прода убери `--reload` и добавь `--workers N`.

**`volumes: - ./:/app` монтирует весь проект в контейнер.** В разработке это удобно (hotreload работает), но в образе для прода этого быть не должно. Сделай отдельный `docker-compose.prod.yml` или используй profiles.

**`image: quay.io/minio/minio:latest`** — `latest` в продакшне это плохая практика. Зафиксируй версию: `quay.io/minio/minio:RELEASE.2025-01-20T...`.

**Нет `.dockerignore`.** При сборке образа в контекст попадает всё, включая `.git`, `__pycache__`, тестовые файлы. Добавь `.dockerignore`.

## 11. Frontend (шаблоны и JS)

Несколько замечаний по фронтенду, раз он есть:

**`fetchJSON` выбрасывает ошибку, которую никто не ловит в dashboard.js и location.js.** Если запрос упадёт (сервер недоступен, 500), пользователь увидит пустую страницу без объяснений. Оберни вызовы в `try/catch` и покажи сообщение об ошибке.

**`window.CAMERA_ID` передаётся через `<script>` в шаблоне.** Это работает, но создаёт глобальную переменную. Лучше использовать `data-*` атрибут на элементе:

```html
<div id="camera-detail" data-camera-id="{{ camera_id }}"></div>
```

```js
const cameraId = document.getElementById('camera-detail').dataset.cameraId;
```

**В `base.html` заголовок страницы — "Камера с камерами и видео"** — опечатка ("Карта с камерами и видео"?).

**auth.js подключается на всех страницах** (через `base.html`), включая страницы без формы логина. Это не ошибка (код проверяет наличие элементов через `getElementById`), но лучше подключать скрипты только там, где они нужны.
